# Issue #4: primary-source notes on the Extension UI surface

Research date: 2026-08-06. Scope: Chrome desktop MV3 and WXT. Statements below are either documented facts, an explicitly labelled inference, or a measurement question.

## Documented facts

### Chrome Side Panel

- `chrome.sidePanel` is MV3-only from Chrome 114 and requires the `sidePanel` manifest permission. A Side Panel is an extension page, separate from the Target Page, and may use extension APIs. A global `side_panel.default_path` applies across sites; `setOptions({ tabId, ... })` creates tab-specific configuration. Chrome documents that a disabled tab hides the panel and returning to a tab where it was open shows it again; navigation to a site where it is disabled closes it. [`chrome.sidePanel`](https://developer.chrome.com/docs/extensions/reference/api/sidePanel)
- `setPanelBehavior({ openPanelOnActionClick: true })` makes the toolbar action toggle the panel. `sidePanel.open()` requires a user action and can target a `tabId` or a `windowId`. `close()` is available from Chrome 141, `onOpened` from 141, and `onClosed` from 142; use of those APIs therefore determines the extension's minimum Chrome version. [`chrome.sidePanel` methods and events](https://developer.chrome.com/docs/extensions/reference/api/sidePanel#methods)
- A tab-specific panel and the default panel are different instances even when they use the same path. Chrome also distinguishes a tab-specific open panel from a global one in the `OpenOptions` contract. [`PanelOptions` and `OpenOptions`](https://developer.chrome.com/docs/extensions/reference/api/sidePanel#type-PanelOptions)
- The current Chromium layout implementation proves that the Side Panel is not painted over unchanged page content. It allocates panel width, insets the remaining horizontal browser content by the visible width, states that the main panel shrinks to accommodate it, and assigns the remaining rectangle to the multi-contents/WebContents view. At constrained widths the content pane may instead slide under the minimum-width panel. [Chromium `BrowserViewTabbedLayoutImpl`](https://github.com/chromium/chromium/blob/f4920aee7dc76a960490f0d959086cf4dfac6306/chrome/browser/ui/views/frame/layout/browser_view_tabbed_layout_impl.cc#L936-L1011), [content bounds](https://github.com/chromium/chromium/blob/f4920aee7dc76a960490f0d959086cf4dfac6306/chrome/browser/ui/views/frame/layout/browser_view_tabbed_layout_impl.cc#L1097-L1122)
- The CSSOM View specification defines `innerWidth` as viewport width and requires a `Window.resize` event when viewport width or height changes; media-query match changes are also observable. Therefore a Side Panel-induced WebContents bounds change can alter layout breakpoints, reflow, and document extent. The exact values and event count in supported Chrome remain fixture measurements, not facts supplied by the Side Panel API docs. [CSSOM View `innerWidth`](https://drafts.csswg.org/cssom-view/#dom-window-innerwidth), [viewport resize steps](https://drafts.csswg.org/cssom-view/#resizing-viewports), [media-query changes](https://drafts.csswg.org/cssom-view/#evaluate-media-queries-and-report-changes)

Permission consequence: choosing Side Panel adds `sidePanel`, contradicting the fixed `activeTab`, `scripting`, and `storage` budget in [ADR-0019](../adr/0019-limit-the-extension-permission-budget.md) unless that decision is explicitly reopened.

### Toolbar action and `activeTab`

- `activeTab` grants temporary access after an explicit extension invocation such as executing the toolbar action. With `scripting`, it permits `scripting.executeScript()` in that tab. Chrome retains the grant on same-origin navigation but revokes it on cross-origin navigation or tab close. UI Torture Lab's product-level Explicit Page Grant is intentionally stricter than this Chrome grant. [Chrome `activeTab`](https://developer.chrome.com/docs/extensions/develop/concepts/activeTab)
- An action popup suppresses `action.onClicked`; action state may otherwise be set per tab. [Chrome `action`](https://developer.chrome.com/docs/extensions/reference/api/action#popup)
- Chromium deliberately does **not** grant tab permissions when the toolbar action toggles a Side Panel, because the panel can be opened without a tab grant and can persist across tab changes. An automatic `openPanelOnActionClick` therefore cannot be treated as UI Torture Lab's Explicit Page Grant. A Shadow UI can instead use the ordinary `action.onClicked` path, which reaches the grant branch before injection. [Chromium `ExtensionActionRunner`](https://github.com/chromium/chromium/blob/c5a70174d6d62736ce2cd2839354737657c02858/chrome/browser/extensions/extension_action_runner.cc#L102-L125)

### WXT candidates

- WXT recognizes `entrypoints/sidepanel.html` (or `sidepanel/index.html`) and emits `/sidepanel.html`; on Chrome this uses the `side_panel` manifest API. [WXT entrypoints](https://wxt.dev/guide/essentials/entrypoints#side-panel)
- The repository's WXT 0.21.3 automatically adds both `side_panel.default_path` and `sidePanel` for that entrypoint. Its development server also adds `tabs` and `scripting` for reload/registration, so permission evidence must come from a production build rather than the development manifest. [WXT 0.21.3 manifest generation](https://github.com/wxt-dev/wxt/blob/wxt-v0.21.3/packages/wxt/src/core/utils/manifest.ts#L385-L410), [development permissions](https://github.com/wxt-dev/wxt/blob/wxt-v0.21.3/packages/wxt/src/core/utils/manifest.ts#L540-L546)
- `createShadowRootUi` mounts an Extension UI into a Shadow Root in the Target Page. WXT isolates styles inside the root and can isolate selected events, but the `shadowHost` itself is an element added to the page DOM and its style is not isolated from page CSS. The default shadow mode is `open`. [WXT content-script UI](https://wxt.dev/guide/essentials/content-scripts.html#shadow-root), [Shadow Root API contract](https://wxt.dev/api/reference/wxt/utils/content-script-ui/shadow-root/interfaces/shadowrootcontentscriptui)
- WXT's `position: "overlay"` wrapper is documented as `0px` by `0px`; a positive `z-index` displays its content over the website. This is a promising non-layout participant, not proof that arbitrary page CSS, fixed children, or overflow cannot affect geometry. [WXT overlay positioning](https://wxt.dev/api/reference/wxt/utils/content-script-ui/types/interfaces/contentscriptoverlaypositioningoptions)
- WXT exposes `mount`/remount and `remove`; `onMount` runs every time `mount()` is called. Content scripts run again on full reload, but do not rerun merely because an SPA changes history/path, for which WXT documents explicit location-change handling. Duplicate-host prevention and Document Runtime reconnection therefore remain application responsibilities to verify. [WXT Shadow Root lifecycle](https://wxt.dev/api/reference/wxt/utils/content-script-ui/shadow-root/interfaces/shadowrootcontentscriptui), [WXT SPA lifecycle](https://wxt.dev/guide/essentials/content-scripts.html#dealing-with-spas)

### DevTools

- Target Page DevTools inspect the page DOM. Because the WXT `shadowHost` is a page DOM element and the default root is open, it should be discoverable from that DOM tree; this is an inference from the two documented contracts, not a Side Panel comparison result. [Chrome DevTools DOM inspection](https://developer.chrome.com/docs/devtools/dom/), [WXT `shadowHost`](https://wxt.dev/api/reference/wxt/utils/content-script-ui/shadow-root/interfaces/shadowrootcontentscriptui#shadowhost)
- Chrome's documented DevTools extension panels are a different surface requiring `devtools_page`; the documentation found does not specify how page element picking, console context selection, docking, focus, or reload behave for an ordinary extension Side Panel. Those are measurement questions. [Chrome DevTools extensions](https://developer.chrome.com/docs/extensions/how-to/devtools/extend-devtools)

## Controlled measurement matrix

The implementation spike used this matrix to exercise both surfaces against controlled fixtures. Results and the reproducible automated subset are recorded in the [UI surface comparison](../../tests/benchmarks/ui-surface-comparison.md); browser-owned interactions that cannot be reproduced headlessly remain release smoke checks rather than inferred guarantees.

| Concern                     | Measurements and transitions                                                                                                                                                                                                                                                                                     |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Geometry                    | `innerWidth/innerHeight`, root `clientWidth/clientHeight`, `visualViewport`, root/body `scrollWidth/scrollHeight`, horizontal overflow, representative element rects, and the active breakpoint/media query.                                                                                                     |
| Resize                      | `Window.resize`, `visualViewport.resize`, `MediaQueryList.change`, `ResizeObserver`, and event ordering/count through open/close and panel-width drag.                                                                                                                                                           |
| Lifecycle                   | Repeated open/collapse/close/remount; full reload; same-origin and cross-origin full navigation; fragment, `pushState`, `replaceState`, popstate, and stable-route SPA changes; back/forward cache; tab switch and tab close. Count hosts, roots, React roots, listeners, ports, and Document Runtime instances. |
| Permissions and association | Generated manifest and install UI; actual `activeTab`/injection success from the configured action path; global versus tab-specific panel behavior; Previous-Target Snapshot association after navigation.                                                                                                       |
| DevTools                    | Dock left/right/bottom and undock; page element picker over the Extension UI; DOM/Shadow Root visibility; console execution context; inspection of the Side Panel document; focus and keyboard shortcuts.                                                                                                        |

## Research conclusion

The Side Panel conflicts with Measurement-Safe UI State because current Chromium deliberately changes the content bounds, and it expands the approved permission budget. The subsequent controlled measurements proved unchanged layout viewport and document extent, zero small-viewport overflow, explicit ownership exclusion, and idempotent lifecycle behavior for the floating Shadow DOM surface; [ADR-0030](../adr/0030-use-a-measurement-safe-shadow-dom-floating-panel.md) records its selection.
